# 微信小程序扫码登录设备管理后台

状态：2026-10-11 按用户最新要求实施：仅网页账号密码登录可作为全量管理员，微信用户只能管理自己关联的设备。此要求取代最初的微信管理员名单方案。

## 目标与参考

在现有 Vue3 设备管理后台增加微信小程序扫码登录，使用独立仓库 `gdgeek/bujiaban-mp` 完成扫描和确认。参照 `jubenmi/pinche` 的实际实现，核对版本为 `c331f2c151d2a89ba679bfa6dae967e08621be29`。

参考代码：

- `apps/api/src/modules/auth/admin-web-login.js`：五分钟登录票据、数据库事务、用户批准、一次性兑换和兑换时重新核验身份。
- `apps/admin-web/src/components/LoginPanel.vue`：二维码展示、轮询、刷新与卸载后的旧请求隔离。
- `apps/miniprogram/src/pages/admin/catalog.vue`：小程序内扫码、确认弹窗和批准接口。

建议复用交互和票据机制，适配本项目的 Session、CSRF 和多个后端。参考项目将同一个 secret 用于扫码批准和领取 JWT；本项目将扫码批准凭据与浏览器兑换资格分开。

## 方案选择

1. **建议：小程序内部扫描普通二维码。** 与参考项目一致；在小程序“我的”页增加“扫码登录设备后台”，扫码后展示目标后端和确认按钮。后台网页说明如何进入小程序扫码。
2. 微信“扫一扫”直接进入小程序确认页。需增加微信小程序码生成或普通链接二维码跳转配置，以及发布后的确认页路径和平台侧联调，实施范围更大。
3. 微信开放平台 PC 扫码登录。需另一套平台配置，不符合此次参照小程序扫码确认的目标。

第一版采用方案 1，保留现有密码登录入口与打卡扫码功能。

## 授权范围

现有 `/admin-api` 的账号可以查看和修改全部设备，不能直接把小程序的 `manager` 角色映射为该账号。

网页账号密码登录为 `role: admin`，默认账号为 `dirui`，可以管理全部设备。微信扫码建立的 Session 为 `role: device_manager`，记录 v2 用户 ID；后续每次读取会话重新核验用户仍存在，每次设备读写由服务层按 `control.user_id` 限制范围。小程序 `manager`、`root` 角色同样受限，无关联设备可登录但返回空列表，关联被撤销后立即失去对应设备权限。角色由 Session 来源派生，不接受客户端角色，不设置微信管理员名单或管理员配置界面。

## 完整流程

1. 网页选择后端后取得该后端 Session 和 CSRF，发送创建票据请求。
2. 后端创建五分钟有效的随机票据。二维码只携带协议版本、目标后端、票据 ID 和批准 secret，不携带微信 Token、浏览器凭据或 Session ID。
3. 网页每两秒读取票据状态；读取接口不建立管理员会话。
4. 小程序解析并严格校验协议与目标后端白名单，展示“不加班设备管理后台”、目标后端域名及授权说明。
5. 用户点击确认后，小程序在目标后端使用新的 `wx.login` code 取得临时 Bearer 身份，再批准票据。该凭据仅保存在此次流程内，不覆盖现有小程序登录缓存。
6. 网页发现票据已批准，使用 CSRF 显式发送兑换请求；后端校验当前浏览器、当前票据、有效期和微信用户身份，原子消费票据，轮换 Session ID，并返回新的 CSRF Token。
7. 网页沿用现有登录成功流程加载当前后端设备与游戏目录。

## 后端与浏览器契约

建议新增接口：

| 方法 | 路径 | 凭据与职责 |
| --- | --- | --- |
| POST | `/admin-api/scan-login/tickets` | 浏览器 Session + CSRF；创建票据并撤销该浏览器此前仍有效的票据 |
| GET | `/admin-api/scan-login/tickets/<id>` | 校验创建浏览器；仅返回状态和截止时间，不登录、不返回凭据 |
| POST | `/admin-api/scan-login/tickets/<id>/consume` | 创建浏览器 + CSRF；仅允许当前票据兑换后台 Session |
| POST | `/admin-api/scan-login/tickets/<id>/cancel` | 创建浏览器 + CSRF；撤销当前票据 |
| POST | `/v2/web-login/tickets/<id>/approve` | `JwtHttpBearerAuth` + 二维码批准 secret；核验有效微信用户并批准其设备管理登录 |

`/admin-api` 沿用直接 JSON 响应，`/v2` 沿用小程序业务响应包装。所有票据响应使用 `Cache-Control: no-store`。接口通过 VerbFilter 限定方法，创建和确认增加节流；错误区分无权限、过期、已使用、无效二维码和服务不可用。

新增数据库迁移和独立票据服务。记录至少包含随机 ID、secret 哈希、浏览器所有者随机值的哈希、状态、授权用户 ID、创建/截止/批准/消费时间。只保存 secret 的哈希。使用事务和有状态条件的更新保证只能批准、消费一次；过期判断使用 `expiresAt <= now`，已批准但未兑换的票据同样受五分钟期限约束。创建时清理已过期的旧票据，避免无限积累。

浏览器所有者值为 Session 内独立生成的随机值，数据库不保存 PHP Session ID。服务端同时检查 Session 中记录的当前票据，刷新后的旧票据不得兑换。终态为 consumed、expired 或 cancelled；重新扫描终态票据需要刷新二维码。

成功密码登录、退出和扫码消费均清除当前票据并撤销其未消费状态；迟到 cancel 只能撤销其自身 ID。创建、消费和取消在持有 Session 锁期间执行。Web 在 consume 进行期间锁定环境切换、登录模式切换、密码登录和退出，待响应及 Session 收敛后再释放，避免仅忽略迟到 JavaScript 响应却已接收 Set-Cookie。

票据记录后端可信配置的 canonical origin，确认和兑换都核验 audience。规范 origin 来自 `ADMIN_SCAN_LOGIN_ORIGIN`，不采用客户端 body 或未经校验的 Host。

扫码登录复用 `AdminAuthService` 的 Session 安全设置和八小时期限，增加独立的微信设备管理登录入口。小程序认证使用 `JwtHttpBearerAuth`，并在身份查询中强制校验签名、有效期及身份来源。

### 现有认证链路的必要修复

原 v1/v2 刷新接口直接解析传入 Token 的 uid 并签发新 Token，没有验证原 Token 的签名或有效期。仅在扫码批准接口验签不足以保护微信身份，因为伪造的 refreshToken 可能先换取合法签名的其他用户 Token。两套身份还共用签名密钥，可能把 v1 player 的 ID 误认成 v2 user 的 ID。此次同步修复身份查询和刷新接口，验证签名、有效期及签名内的 `identityDomain`（`v1-player` / `v2-user`），拒绝伪造、畸形、过期、跨域及旧无域 Token，并加入不能冒用其他用户的回归测试。旧 Token 用户需重新登录；v1 刷新接口停止记录含凭据的请求。

### 关联设备接口范围

现有 v2 设备分配接口可以让普通微信用户给自己关联他人的设备，Setup 标准 CRUD 也缺少设备归属检查。为使权限约束有效，此次统一限制 Device index/view/update/manage 和 Setup CRUD 为 `control.user_id` 关联范围，包括微信 root。Setup 更新不得重绑 `device_id`；微信 Bearer 不可调用全局设备 create/delete/assign/unassign 或 Root/Manager 分配入口。v2 仅接受严格验证的 v2 Bearer，不读取网页 Session。小程序移除全局管理入口和 root 页面注册，保留关联设备查询与配置编辑。

当前微信登录在缺少 unionid 时仍访问未初始化的用户。此次目标后端重新认证路径必须返回确定结果：有 unionid 时沿用现有匹配；缺少 unionid 时只允许按微信服务端返回的 openid 匹配已有用户，无法匹配时返回明确登录失败，不创建不完整用户、不签发 Token。不得接受客户端自报的 openid 或 unionid 作为身份。

## 多后端约束

2026-10-11 核对实际 Portainer 配置：B0/B1 与 x.4mr.cn 均指向同一个 wechat 容器和同一数据库，因此迁移执行一次，服务配置一个规范扫码 origin；Web 两个代理入口仍分别保存 Session。

目前网页后端由运行时配置生成，`b0`、`b1` 是该部署的代理编号，不作为跨应用的永久后端标识。小程序目前固定请求 `https://x.4mr.cn/v2`，不能假定其 Token 在 B0/B1 有效。

扫码协议使用后端的规范 HTTPS origin，必须与小程序构建配置中的可信后端名单完全匹配；不接受二维码提供的任意 URL、用户信息、路径、重定向或相似域名。允许的初始 origin 为现有管理后台使用的 B0/B1，具体配置在实现文档中列明。

小程序针对白名单目标执行微信 code 交换和后续请求，不调用会自动附加全局 Bearer 的任意 URL 请求逻辑。新取得的目标环境 Token 不写入 `AR_CHECKIN_OPENID`。目标后端必须配置与 `bujiaban-mp` 相同的小程序 AppID，合法请求域名在微信平台配置后才能真机使用。

## 前端与小程序改动边界

- Web 增加独立扫码组件和 API 契约，沿用现有登录页视觉样式。
- 刷新二维码、切换后端、切回密码登录、登录成功和组件卸载时停止轮询并隔离旧响应。
- 每次操作固定创建时的后端上下文，不在失败时切换环境；服务端撤销与当前票据检查防止迟到响应重新建立旧登录。
- 小程序新增扫码解析、受限目标请求模块和确认页，在“我的”页提供入口；原打卡扫码分支继续使用原协议。
- 不把二维码 secret 放入页面导航 URL、日志、埋点或错误详情；页面间传递使用临时内存状态。
- 完成后分别检查根仓库与 `bujiaban-mp` 的 diff、测试和发布说明，保留已有未提交变更。
